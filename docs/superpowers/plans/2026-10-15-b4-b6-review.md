## Decisions proposed for approval

1. **One UI switch:** `NEXT_PUBLIC_DATA_SOURCE=fixtures|api`, default `fixtures`; `NEXT_PUBLIC_API_BASE_URL` is a location, not a second mode flag. Backend `API_MODE=fixtures|live` selects route implementation independently. A live graph API may coexist with explicitly labelled fixture agent routes until A10; never claim fixture triage is real.
2. **Friday issue selection:** accept `?issue=<encoded stable Issue key>` on `/t/[tenant]`; live mode has a small issue-key input/empty state rather than borrowing the synthetic fixture issue. Before A10, show graph/counts without fabricated triage; after A10, use actual triage/run responses.
3. **Public live apply:** spec §12 says the public UI is read-only except dry runs and feedback, while §11 supplies an Apply switch. Recommended resolution: public HTTP/UI allows dry-run only; `apply_triage(..., dry_run=False)` is available internally for B7's verified webhook and trusted stdio MCP, still subject to sandbox/collaborator checks. Require explicit owner approval before permitting public HTTP live writes. No new auth system in B6.
4. **No evidence is not an error:** empty graph/path responses are visible empty states. Do not fabricate a connecting path when the four-hop evidence-only query cannot reach a citation.
5. **Estimate:** B4 ~100 min, B5 ~110 min, B6 ~90 min (five hours total, excluding waits for A and deployed acceptance). If any task exceeds two hours, stop and propose a smaller slice. B5 animation and hover polish are first to defer; never defer citation selection, trace, sandbox refusal, or deployment acceptance.

## A/B handoff gates

These are **requested interfaces**, not claims about code that already exists. Agree import paths and signatures with A before implementation; if A has an equivalent interface, adapt B's adapter rather than add a second graph stack.

- A supplies graph connection/query loading and named `subgraph.cypher`, `stats.cypher`, `explain_path.cypher`, `record_actions.cypher`. B4 defines response mapping and caps; A owns Cypher. Proposed B-facing graph adapter methods are in B4.
- `explain_path(tenant: str, from_key: str, to_key: str) -> ToolResult`, where `data` validates as `PathData`; includes executed query text and empty-result semantics. A confirms sync/async behavior before B wires it.
- A supplies an action context lookup with the same tenant/run semantics as `recall_run`: B6's `ApplyContext` includes the handled Issue identity and the persisted proposed actions. `RecallRunData` alone lacks `incoming`, so it cannot establish write eligibility.
- A supplies a parameterized way to execute `record_actions.cypher` with `results=[{"key": action_key, "status": ..., "note": ...}]`; verify action ownership belongs to the selected tenant/run before updating.
- A wires the B-owned `apply_triage` into A6's stdio MCP; B does not edit `api/mcp_server.py`. A10 records the actions B6 consumes; fixture runs are not live records.
- Agree a trustworthy last-ingest timestamp source with A. Until supplied, use `last_ingest_at: null`; never substitute API startup time or a file modification time.
